# 数值管理规范（Numeric Management Convention）

> 本规范为《炽窑》（*Ember's Kiln*）项目的**硬性数值纪律**。所有程序代码中出现的数值（配置参数、阈值、奖励、概率、次数上限、缩放系数等）均受其约束。
> 配套台账：`AI_Studio/Design/NUMERIC_LEDGER.md`（每一个数值的闭环追踪记录）。

---

## 1. 核心铁律

1. **代码不得硬编码玩法数值。** 任何影响玩法/平衡的数值必须落在数据文件中：`data/*.json`（运行时由 `GameData` 加载）或 `AI_Studio/Design/*.json`（文档镜像）。脚本只读取，不写死。
2. **未定义数值 → 提报策划，不得自填。** 当实现需要某个策划案尚未定义的数值时，实现方**必须停下来**提请策划团队决定，严禁拍脑袋填一个"先跑起来"。
3. **数值须策划确认后方可写入代码。** 任何数值进入代码（数据文件）前，须有明确的策划确认记录（见 §3 闭环）。
4. **数值落地后必须回填策划案。** 确认值写入数据文件的同时，回填进策划案/台账，保证"代码里的数"与"文档里的数"一致、可追溯。
5. **改数值 = 改数据，不是改脚本。** 平衡调整只动 `data/*.json`，不碰 `scripts/` 里的逻辑（除非是新增机制）。

---

## 2. 角色

| 角色 | 职责 |
|------|------|
| **策划团队（数值/战斗/内容）** | 提出数值、确认数值、在台账签字、维护策划案中的数值定义。本项目中用户即策划裁决方。 |
| **实现方（Programmer / Agent）** | 发现数值需求 → 提报 → 等确认 → 仅写入数据文件 → 回填台账 → 跑验证。不得自行定数。 |
| **QA** | 核对"代码数值 == 台账数值 == 策划案数值"，发现三处不一致即报 Bug。 |

---

## 3. 闭环工作流（必须完整、无遗漏、可执行）

```
[1] 提案（Proposal）
     实现方或策划提出"需要数值 X，用途 Y"。
     在 NUMERIC_LEDGER.md 新增一行：状态=「提议中」，记录用途/模块/提议值。

        ↓

[2] 策划确认（Sign-off）
     策划团队审核并给出"确认值"。
     台账该行：状态=「已确认」，填 确认值 / 确认人 / 日期。
     ⚠️ 无确认值，禁止进入下一步。

        ↓

[3] 代码写入（Write）
     仅把确认值写入对应数据文件（data/*.json），脚本中不得出现该字面量。
     台账该行：来源=数据文件路径+字段；状态=「已落地」。

        ↓

[4] 策划案回填（Backfill）
     确认值回填进策划案（GAMEPLAY_ENRICH_PLAN.md / BALANCE_TABLE.json / 本台账"设计记录"列）。
     台账该行：设计记录=文档位置；状态=「闭环完成」。

        ↓

[5] 验证（Verify）
     跑对应测试/集成验证，确认数值按预期生效。
     台账该行：附验证结果（如 RESULT:PASS）。
```

**可执行检查清单（每次动数值都过一遍）：**
- [ ] 该数值在策划案/台账中是否存在？
- [ ] 不存在 → 是否已提报策划并拿到确认值？（禁止自填）
- [ ] 确认值是否只写进了数据文件，脚本里没有字面量？
- [ ] 台账是否新增/更新了该数值的闭环记录？
- [ ] 策划案是否已回填？
- [ ] 验证是否通过？

---

## 4. 既有数值的归类要求

项目已有数值（难度系数、精英频率、玩家 HP/能量、窑温阈值、Boss 基础 HP、编成表等）统一登记进 `NUMERIC_LEDGER.md`，作为**唯一可追溯来源**。新增数值一律先入台账再入代码。

---

## 5. 与本规范冲突时的优先级

`用户最新明确要求` > `NUMERIC_LEDGER.md / 本规范` > `GAMEPLAY_ENRICH_PLAN.md` > 其他设计文档 > Agent 默认行为。

> 用户在本会话中明确指令"编写平衡 sweep harness 并据此建立数值规范"——其中 harness 的自有参数（模拟次数、离群阈值、build 定义）由实现方提议、经该指令确认，已登记进台账闭环，符合本规范。
